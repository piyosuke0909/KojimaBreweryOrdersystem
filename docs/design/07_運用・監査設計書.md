# 運用・監査・セキュリティ設計書

作成日: 2026-10-19  
版: 2.0（TypeScript + Hono + Cloudflare D1 対応版）

## 1. セキュリティ設計

### 1.1 顧客側（LINE / LIFF）認証・認可
- **ID Tokenのサーバーサイド検証**:
  - LIFFブラウザから送信されるリクエストには `Authorization: Bearer <LINE_ID_TOKEN>` ヘッダを付与する。
  - Honoの認証ミドルウェアでLINE Platformの検証エンドポイント（またはJWK署名検証）を用いてID Tokenを検証し、改ざん不可能な `lineUserId` を取得する。リクエストボディやクエリパラメータで直接送られた `lineUserId` や `companyId` は一切信用しない。
- **テナント分離（データアクセス制御）**:
  - 取得した `lineUserId` から `line_users` テーブル（`status = 'active'`）を引き、紐づく `company_id`（取引先ID）を特定する。
  - 商品単価取得・注文作成・注文履歴取得・注文詳細・注文編集・キャンセルのすべてのクエリにおいて、必ずサーバー側で `WHERE company_id = <特定したcompany_id>` を強制付与し、取引先Aが取引先Bの契約単価や注文データを閲覧・操作できないようにする。

### 1.2 招待QRコードのセキュリティ
- 招待URL（`/invite?t=<ランダムトークン>`）には取引先ID等の内部情報を含めず、暗号論的に安全な乱数（256bit以上）を使用する。
- Cloudflare D1の `invitations` テーブルには生トークンを保存せず、**SHA-256ハッシュ値（`token_hash`）**のみを保存する。監査ログにも生トークンは記録しない。
- 招待QRコードには**有効期限（`expires_at`）**と**最大登録可能人数（`max_uses`）**を設定でき、管理画面（`A-08`）からいつでも即時無効化（`revoked`）または再発行が可能。
- すでに別企業へ紐付いている `lineUserId` が他社の招待QRコードを読み取った場合、自動で所属を上書きせず拒否する。

### 1.3 管理者ポータル認証
- 管理ポータル（`/admin/*`）は未認証でのアクセスを禁止し、`A-00 管理者ログイン` 画面での認証を必須とする。
- パスワードは安全なハッシュ方式（PBKDF2 / Argon2 / bcrypt）で `admins.password_hash` に保存する。
- ログイン成功後は署名付きJWTを `HttpOnly; Secure; SameSite=Strict` Cookieで発行し、すべての管理APIで検証する。

### 1.4 機密情報の管理
- LINE Channel ID / Secret、LIFF ID、JWT署名シークレット、メール送信APIキー等はソースコードに含めず、Cloudflare Workersのシークレット環境変数（`wrangler secret`）で安全に管理する。

## 2. 排他制御・冪等性・データ保全設計

### 2.1 二重注文防止（冪等性保証）
- 注文確認画面（`L-07`）を表示するたびに一意の `request_id`（UUID v4）を発行する。
- 注文確定APIでは、まず `order_requests` テーブルおよび `orders.request_id` のUNIQUE制約を確認し、すでに処理済みの `request_id` であれば新規注文を作成せず、作成済みの注文データをそのまま返却する。

### 2.2 注文編集ロックと楽観ロック
- 注文編集画面（`L-11` / `A-04`）を開いた際、`orders` テーブルの `edit_locked_by` と `edit_lock_expires_at`（現在時刻＋10分）を更新してロックを取得する。
- ロック有効期限内に別のユーザーが開いた場合は閲覧のみとする。
- 保存時には `version` カラムの一致を確認（`WHERE id = ? AND version = ?`）し、更新時に `version = version + 1` とすることで競合上書きを完全に防止する。

### 2.3 マスタ変更からの過去データ保護（スナップショット設計）
- **注文データ**: 注文確定時点の商品名・容量・単価・配送先名・郵便番号・住所・配送料・税率・税計算単位を `orders` および `order_items` にスナップショット保存する。後日の商品価格改定や配送先住所変更によって過去注文の内容が変化しない。
- **請求書・納品書データ（R2不使用・D1スナップショット方式）**:
  - 請求書発行時（および再発行時）には、その時点の「宛先・対象注文明細・税抜合計・消費税額・税込合計・小島醸造の会社情報・適格請求書登録番号・振込先銀行口座」のすべてを `invoice_histories.snapshot_json` に完全保存する。
  - これにより、外部オブジェクトストレージ（Cloudflare R2等）を一切使わずに、後日会社移転や口座変更があっても、発行当時の版（v1, v2...）の帳票を画面プレビュー（`A-24`）から100%同一内容で復元・PDFダウンロードできる。

## 3. 監査ログ設計

### 3.1 監査記録対象アクション一覧
以下の主要操作を行う際、Cloudflare D1のバッチトランザクション（`db.batch()`）を用いて、**業務データの更新と監査ログ（`audit_logs`）の記録を同一アトミック処理**として実行する。

| カテゴリ | 操作種別コード (`action`) | 記録タイミング |
|---|---|---|
| **取引先・認証** | `COMPANY_CREATE` / `COMPANY_UPDATE` | 取引先の追加・基本情報変更・有効/無効切替 |
| | `ADDRESS_CREATE` / `ADDRESS_UPDATE` | 配送先の追加・変更 |
| | `INVITE_ISSUE` / `INVITE_REVOKE` | 招待QRコードの発行・上限変更・無効化 |
| | `LINE_USER_REGISTER` / `LINE_USER_UNLINK` | LINE担当者の初回登録・管理者による紐付け解除 |
| **商品・単価** | `PRODUCT_CREATE` / `PRODUCT_UPDATE` | 商品の追加・標準卸価格や販売状態の変更 |
| | `COMPANY_PRICE_UPDATE` | 取引先別販売単価の設定・改定 |
| **注文** | `ORDER_CREATE` | 新規注文の確定 |
| | `ORDER_EDIT` | 顧客または管理者による注文内容の直接編集（`order_revisions` も同時作成） |
| | `ORDER_CANCEL` | 顧客または管理者による注文キャンセル |
| | `ORDER_STATUS_CHANGE` | 注文ステータスの変更（受付済→確認済→配送準備中→発送済→完了） |
| **配送・設定** | `SHIPPING_RULE_UPDATE` / `CALENDAR_UPDATE` | 配送ルール・配送カレンダーの変更 |
| | `PACKAGING_UPDATE` / `YAMATO_RATE_UPDATE` | 梱包マスタ・ヤマトサイズ・ヤマト運賃の変更 |
| | `SETTINGS_UPDATE` / `COMPANY_INFO_UPDATE` | 税設定・会社情報・銀行口座・帳票設定の変更 |
| **請求** | `INVOICE_ISSUE` | 請求書の発行および対象注文の請求ロック |
| | `INVOICE_CANCEL` | 請求の取消および対象注文の請求ロック解除 |
| | `INVOICE_REISSUE` | 請求書の再発行（新版作成・再ロック） |
