# LINE認証と企業紐づけ

## 登録フロー

1. 取引先ごとの招待QRから `https://liff.line.me/{LIFF_ID}/invite?t=...` を開きます。招待・注文ではLIFFがLINE公式の認証へ自動で進み、通常の「LINEでログインして登録」画面を挟みません。認証を取り消した場合や失敗した場合だけ、再認証の操作を表示します。商品紹介・お問い合わせの閲覧ではログインを強制しません。
2. IDトークンがある場合は、LINE公式APIで発行元・Loginチャネル・有効期限を検証します。IDトークンがない場合は、LIFFのアクセストークンを検証し、LoginチャネルID・有効期限・profileスコープを確認してから、LINE公式プロフィールAPIから本人のLINE IDを取得します。
3. 本人確認済みの利用者と招待先をサーバーに一時保存します。この時点では企業の担当者登録や招待の使用人数更新は行いません。公式アカウント `@060ucble` の友だち状態を確認し、未追加・ブロック中なら追加を案内、追加済みなら「小島醸造のトークを開く」を表示します。LINEログインだけで友だち追加は完了しません。
4. 友だち追加後、小島醸造のトークにあるリッチメニュー「注文」を押します。その画面でもLINEの認証情報を検証して本人の招待先を復元し、友だち追加を確認できた初回利用者に担当者名の入力画面を表示します。「登録して注文へ進む」で認証情報を再検証し、サーバー保存済みの招待先へ登録します。クライアントから送られた企業IDやプロフィールの利用者IDを紐づけ先の判定に使いません。
5. 招待の有効期限・状態・上限・既存の企業紐づけを確認し、登録人数の更新、LINE利用者の登録、監査を同じトランザクションで保存します。
6. 署名済みCookieを発行し、企業に所属する利用者として注文画面を開きます。以後のAPIでもDB上の利用者・企業状態を確認します。登録済みの利用者はリッチメニューから担当者名を入力せず注文へ進めます。同じ企業のQRを開き直した場合は、友だち追加・トークを開く案内を表示するため、以前に友だち追加せず登録した方も同じQRを使えます。LIFF未設定のローカル検証環境では、従来のデモ登録を維持します。

## 2026-10-22の友だち追加・トークへの引き継ぎ

以前の登録画面は本人確認から直接担当者登録へ進み、友だち追加の確認と公式トークへの移動がありませんでした。企業との紐づけが完了しても友だちになっていない状態は、このフローで起こり得ます。今回の変更では、QR → LINE本人確認 → 友だち追加 → 公式トーク → リッチメニュー「注文」 → 初回の担当者名 → 注文の順に案内します。

友だち追加とLINEの同意画面では、本人の操作が必要です。アプリが勝手に友だち追加したり、OSのアプリ切替を確実に自動実行したりすることはできません。公式プロフィール・トークへの移動は画面のボタンから行います。未追加や確認失敗を追加済みとして扱わず、追加・ブロック解除・再確認を案内します。

引き継ぎは `line_invitation_handoffs`（migration `0005`）で管理します。キーは検証したLoginチャネルIDと利用者IDのSHA-256、招待先・一度だけ使える識別子・24時間の保持期限を保存します。LINEのトークンは保存しません。Safari／ChromeとLINE内ブラウザーでCookieやストレージが別でも、同じ本人の検証を通じて復元します。別のLINEアカウントでは復元できません。招待を開き直すと保持期間を更新し、違う招待に切り替えた場合は古いフォームからの登録を拒否します。

24時間は登録途中の引き継ぎ情報の保持期間です。保存済みQRの有効期限や人数上限は変更しません。QR無効化・削除・期限・上限と企業状態を再確認し、最終登録と引き継ぎ消費を同じトランザクションで処理します。同時に登録しても二重登録・人数の二重消費を防ぎます。

変更前の本番ではLIFFのエンドポイント、`openid`・`profile`、公式アカウント連携、標準リッチメニューの「注文」URLが正しいことを読み取り確認しました。これは個々の利用者の友だち状態や、新しいフローの端末操作の確認とは別です。

現在のLINE Loginチャネルは `2011901973`、Workers用LIFFは `2011901973-juZ5QTYX`、Messaging APIチャネルは `2011903727` です。本番Worker・リッチメニューへの反映、実アカウントの企業登録、署名済みWebhookとの利用者一致、登録完了通知・テスト注文通知の実受信を確認しました。Loginチャネルの公開状態はユーザーから「公開済み」と報告を受けています。LINE内のメニューからA商店の注文画面が開いたこともユーザーから確認しました。別の実LINEアカウントによる登録は未確認です。顧客本人の認証にはLoginチャネルを使い、通知・リッチメニュー用のトークンと混同しません。

## 2026-10-20の修正

LINEプロフィールを取得できていても、`liff.getIDToken()` が `null` だと「LINEでログインしてから登録してください」と表示し、企業登録へ進めない不具合がありました。ログインと登録で同じ認証情報の選択処理を使い、IDトークンがない場合のアクセストークンによる本人確認を追加しました。不正なIDトークンが渡された場合に、別のトークンで検証を迂回することはありません。

未登録状態は `LINE_USER_NOT_REGISTERED` で返し、本人確認済み・企業登録待ちとして扱います。LINEアカウントを切り替えた際に、以前の利用者のCookieや企業表示が残らないようにしました。認証完了前の招待判定や、古い利用者に対する招待情報での画面遷移も防止しています。

認証情報を取得できない場合は、LINE認証をやり直す操作を表示します。招待URLを維持したまま再認証するため、元のQRを再利用できます。LINEの友だち追加だけで企業を自動選択することはありません。

- `tests/line-invitation-handoff.test.ts`: 実HonoとSQLiteで、本人に限定した引き継ぎ、チャネルの違い、保持期限、招待切替、無効化・上限、同時登録、監査失敗時のロールバックを確認します。
- `tests/e2e/line-auth.spec.ts`: 実ブラウザーの画面で、自動認証と取り消し・初期化失敗、友だち未追加・状態確認失敗、別ブラウザーでの同じ本人の復元、別人の拒否、担当者名から注文への移動、登録済みQRのトーク案内を確認します。SDKの置換はテスト時の通信差し替えのみで、本番コードにテスト用の認証機構は追加しません。
- 本番では、実際の利用者のLINEで「登録完了」が表示され、管理画面の取引先詳細 → LINE利用者に登録されたことを最後に確認します。開発テストの成功だけを、本人のLINEアカウントによる登録成功とは扱いません。
- 複数利用者の登録、同時登録、アカウント切替の追加結果は [複数LINEアカウント検証](複数LINEアカウント検証.md) に記録しています。

アクセストークン、IDトークン、Cookieをログやチャットへ出しません。招待の照合にはトークンのハッシュを使用し、発行時のURLは登録対象者への案内にだけ使用します。
