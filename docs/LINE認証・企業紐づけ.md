# LINE認証と企業紐づけ

## 登録フロー

1. LIFFを設定した環境では、取引先ごとの招待QRから `https://liff.line.me/{LIFF_ID}/invite?t=...` をスマートフォンのLINEアプリで開き、LIFFの初期化を完了します。LIFF未設定の開発環境では、従来の自サイト `/invite?t=...` を使います。
2. IDトークンがある場合は、LINE公式APIで発行元・Loginチャネル・有効期限を検証します。IDトークンがない場合は、LIFFのアクセストークンを検証し、LoginチャネルID・有効期限・profileスコープを確認してから、LINE公式プロフィールAPIから本人のLINE IDを取得します。
3. 本人確認済みの利用者がまだ企業に登録されていない場合は、担当者名の入力画面を表示します。プロフィールの取得は氏名の初期表示用であり、IDトークンによる本人確認を妨げません。
4. 「登録する」で認証情報を再検証し、招待トークンのハッシュから企業を決定します。クライアントから送られた企業IDやプロフィールの利用者IDを紐づけ先の判定に使いません。
5. 招待の有効期限・状態・上限・既存の企業紐づけを確認し、登録人数の更新、LINE利用者の登録、監査を同じトランザクションで保存します。
6. 署名済みCookieを発行し、企業に所属する利用者として注文画面を開きます。以後のAPIでもDB上の利用者・企業状態を確認します。

現在のLINE Loginチャネルは `2011901973`、Workers用LIFFは `2011901973-juZ5QTYX`、Messaging APIチャネルは `2011903727` です。本番Workerとリッチメニューへの反映は完了しています。新LIFFでの実アカウントの再登録・通知と、Loginチャネルの公開状態の確認はまだ完了していません。顧客本人の認証にはLoginチャネルを使い、通知・リッチメニュー用のトークンと混同しません。

## 2026-10-20の修正

LINEプロフィールを取得できていても、`liff.getIDToken()` が `null` だと「LINEでログインしてから登録してください」と表示し、企業登録へ進めない不具合がありました。ログインと登録で同じ認証情報の選択処理を使い、IDトークンがない場合のアクセストークンによる本人確認を追加しました。不正なIDトークンが渡された場合に、別のトークンで検証を迂回することはありません。

未登録状態は `LINE_USER_NOT_REGISTERED` で返し、本人確認済み・企業登録待ちとして扱います。LINEアカウントを切り替えた際に、以前の利用者のCookieや企業表示が残らないようにしました。認証完了前の招待判定や、古い利用者に対する招待情報での画面遷移も防止しています。

認証情報を取得できない場合は、LINE認証をやり直す操作を表示します。招待URLを維持したまま再認証するため、元のQRを再利用できます。LINEの友だち追加だけで企業を自動選択することはありません。

## 検証範囲

- `tests/line-customer-auth.test.ts`: 実HonoとSQLiteで、アクセストークンによる登録・企業への紐づけ・登録後セッション、IDトークンとの優先関係、誤ったLoginチャネル・期限・権限の拒否、古い顧客セッションの破棄、別企業の上書き拒否を確認します。LINE公式APIはテスト内の応答に置き換えます。
- `tests/e2e/line-auth.spec.ts`: 実ブラウザーの画面で、IDトークンなしの登録、プロフィール取得失敗、古い企業の状態が残る場合、再認証と招待URLの保持を確認します。SDKの置換はテスト時の通信差し替えのみで、本番コードにテスト用の認証機構は追加しません。
- 本番では、実際の利用者のLINEで「登録完了」が表示され、管理画面の取引先詳細 → LINE利用者に登録されたことを最後に確認します。開発テストの成功だけを、本人のLINEアカウントによる登録成功とは扱いません。
- 複数利用者の登録、同時登録、アカウント切替の追加結果は [複数LINEアカウント検証](複数LINEアカウント検証.md) に記録しています。

アクセストークン、IDトークン、Cookieをログやチャットへ出しません。招待トークンはハッシュだけを保存し、発行時のURLは登録対象者への案内にだけ使用します。
